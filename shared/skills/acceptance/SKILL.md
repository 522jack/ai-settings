# Приёмка

Перед записью прочитайте `$HOME/dotfiles/ai/shared/rules/task-report.md`. Используйте общий `swarm-report/<task-slug>.md`, раздел `## Acceptance`; task-slug наследуется от main и не меняется для checks. Только main пишет отчёт; специалисты возвращают компактные результаты.

Вход: slug, spec/AC/PR/issue/test plan либо bug reproduction. Без источника проверки остановитесь с missing input: write-spec для требований, generate-test-plan для TC, debug artifact для бага. Исследовательский QA без сценария — отдельный manual-tester, не acceptance.

1. Определите project_type (`android|ios|web|desktop|backend-jvm|backend-node|cli|library|generic`), UI surface, ecosystem. Непустой spec.platform приоритетен: первая платформа каноническая, остальные в platforms; override spec/user фиксируется. Не угадывайте generic UI.
2. Прочитайте relevant spec frontmatter (`platform/surfaces/risk_areas/non_functional/acceptance_criteria_ids/design.figma`) и разделы `## Test plan` и `## Debug` общего отчёта и permanent test plan. Для выбора `test_plan_source: receipt|mounted|on-the-fly|absent` прочитайте [source-branches.md](references/source-branches.md). Dизайн без AC разрешает только design review, не VERIFIED функциональности.
3. Android/iOS runtime QA только при явной просьбе пользователя в текущем запросе (`mobile_manual_requested`); UI/spec/risk/test plan не включают его автоматически. Policy SKIPPED не понижает verdict. Для разрешённого runtime UI check сохраните краткий сценарий под `## Acceptance`; bug scenario инвертирует reproduce в expected fixed behavior. Web/desktop instrumentation проверяйте только если контракт задаёт её; mobile также требует opt-in.
4. Зафиксируйте code+scope+environment. Upstream блок `quality` раздела `## Quality` общего отчёта (status/date/code_hash/scope_hash/environment/review/checks/escalate) или independent review/build result может покрыть check только при доказанном exact-state совпадении, включая working tree; Date/HEAD сами по себе недостаточны. Reused check сохраняет pointer/evidence, в том числе команды и исходы из `review`/`checks`; одна ссылка без exact-state evidence недостаточна. Upstream FAIL нельзя скрыть: minimum PARTIAL, при blocker FAILED.
5. Для fan-out выберите actual triggered checks из [check-selection.md](references/check-selection.md). Перед запуском прочитайте [state-and-schema.md](references/state-and-schema.md), сохраните полный Planned Checks; [subcheck-prompts.md](references/subcheck-prompts.md) загружайте только для выбранных checks. Независимые проверки параллельны, не пересылайте findings между reviewers.
6. При агрегации прочитайте [aggregation.md](references/aggregation.md). Planned result missing → FAIL/blocked_on, никогда VERIFIED; намеренно omitted policy checks — SKIPPED. Обновите только `## Acceptance` в общем отчёте: VERIFIED|FAILED|PARTIAL, inputs/state, plan/results, findings, evidence, recommendation. Chat: verdict, главные failures/skips, путь и нужный следующий шаг.

На fix-loop/re-entry прочитайте [re-verification.md](references/re-verification.md). Повтор checks только после реальной мутации code/scope/env либо явно запрошенного эксперимента; unchanged FAIL остаётся FAIL с прежним evidence, не запускается ради «нового раунда». Max 3 содержательных cycles; persistent genuine block → evidence+escalation. Локальные разрешённые fixes делегируйте, новые tests только opt-in; не расширяйте scope, не принимайте риск за пользователя и не ship при unresolved blocker без соответствующего решения.
