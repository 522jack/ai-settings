# Раунды интервью — банк вопросов, структура раунда и запросы для раундов

Полный playbook фазы 2. В SKILL.md находятся только контракт цикла раундов и критерии выхода.
Всё, что раунд фактически *говорит* пользователю, находится здесь.

---

## Чек-лист функциональности (выполнить до формулировки вопросов)

После завершения исследования пройдитесь по чек-листу. Любой применимый вопрос без ответа
становится вопросом пользователю или записью в spec.

- [ ] **Разрешения ОС** — нужно ли функциональности запрашивать разрешения
      (notifications, camera, location, contacts, storage)? What happens if denied?
- [ ] **Поведение платформы** — работает ли это по-разному на разных ОС/устройствах?
- [ ] **Предусловия** — есть ли внешние шаги настройки (конфигурация консоли, аккаунты
      accounts, API keys, entitlements) that can't be automated in code?
- [ ] **Состояния ошибок** — что может завершиться сбоем? Что видит пользователь при сбое?
- [ ] **Безопасность** — раскрывает ли это чувствительные данные, требует auth или затрагивает
      credentials?
- [ ] **Производительность** — есть ли риск блокировки main thread, чрезмерного потребления памяти или
      battery drain?
- [ ] **Обратная совместимость** — меняет ли это существующее поведение, от которого кто-то зависит?
- [ ] **Качество паттернов** — отметил ли Critical Evaluation какой-либо существующий паттерн как
      problematic?

## Раунд 1: представьте варианты подхода (если выполнялась Critical Evaluation)

Если Critical Evaluation подготовила 3 варианта подхода, представьте их **до** остальных вопросов.
Это самое важное решение — оно определяет всё остальное.

```
По результатам исследования доступны следующие подходы к реализации:

**Option A — Radical:** {name}
{2-3 sentences describing the approach}
Trade-offs: {pros} / {cons}
Best when: {context where this wins}

**Option B — Classic:** {name}
{2-3 sentences describing the approach}
Trade-offs: {pros} / {cons}
Best when: {context where this wins}

**Option C — Conservative:** {name}
{2-3 sentences describing the approach}
Trade-offs: {pros} / {cons}
Best when: {context where this wins}

Рекомендация: вариант {X} — {обоснование в одном предложении}
Или опишите собственный подход: ___
```

Прежде чем продолжать, дождитесь выбора пользователя. Выбранный подход становится
baseline для всех последующих вопросов.

---

## Синтезируйте пробелы

После выбора подхода разделите оставшиеся результаты на три группы:

- **Уже известно** — исследование дало ясный ответ, спрашивать не нужно.
- **Предлагаемые значения по умолчанию** — исследование указывает направление; предложите его для подтверждения.
- **Настоящие пробелы** — требуют решения пользователя.

Спрашивайте только о настоящих пробелах. Предлагайте значения по умолчанию как рекомендации,
которые пользователь подтверждает или переопределяет.

---

## Формат вопроса

Each question in a round:

```
**Q: {question}**
→ Рекомендация: {ответ} — {краткое обоснование}
→ Альтернатива: {другой вариант}
→ Альтернатива: {ещё один вариант, если уместно}
→ Или опишите предпочтение: ___
```

Пропускайте вопросы, где рекомендация очевидна, а ответ существенно не меняет архитектуру.
Зафиксируйте такие решения в секции «Decisions Made» spec.

---

## Структура раунда

Each round:

1. Представьте уже понятое (кратко — это даёт пользователю контекст).
2. Задайте все текущие открытые вопросы с рекомендуемыми ответами.
3. Дождитесь ответов.
4. Запишите ответы в файл состояния.
5. Проверьте, не появились ли новые пробелы из ответов.
6. Если пробелы остались → ещё один раунд. Если всё завершено → переходите к черновику.

**Предел: максимум 100 раундов интервью.** Если после 100-го раунда остаются пробелы,
запишите их как открытые вопросы в spec (по возможности non-blocking) и перейдите к черновику.
Оставшиеся блокеры покажите пользователю на этапе ревью.

## Разбиение крупной функциональности на фазы

Если функциональность охватывает несколько независимых фаз разработки, предложите
поэтапный подход:

```
Эта функциональность масштабна. Предлагаемые фазы:

**Phase 1 — {name}:** {what it delivers and why first}
**Phase 2 — {name}:** {what it adds, depends on Phase 1}
**Phase 3 — {name}:** {what it adds}

Рекомендация: описать в spec и полностью реализовать фазу 1 до подготовки spec для фазы 2.
Реальная обратная связь по фазе 1 поможет спроектировать фазу 2.

Продолжить поэтапно или сразу описать всю функциональность?
```

При поэтапном подходе spec покрывает только фазу 1. Включите секцию «Future Phases» для
запланированного, но ещё не описанного.

---

## Раунд обсуждения после ревью

После завершения self-review и `multiexpert-review` (фаза 4), если любой из них выявил
проблемы или открытые вопросы, откройте ещё один пользовательский раунд с тем же форматом
вопросов выше. Он может вернуть обычный цикл раундов для закрытия оставшихся пробелов.

Когда пользователь удовлетворён и проблем больше нет, измените статус spec с
`draft` на `approved` и перейдите к сохранению.
