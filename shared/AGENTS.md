# Глобальные правила AI-агентов

## Неоспоримые правила

Правила, не подлежащие обсуждению. Их нарушение — ошибка, а не вопрос суждения.

- Язык общения - русский
- **Никогда не обходить git-хуки** (`--no-verify`, `--no-gpg-sign`, `-c commit.gpgsign=false` и т.п.) без явного запроса пользователя. Если хук падает — расследовать и устранять корневую причину.
- **Никогда не коммитить и не пушить напрямую в main/master/develop.**
- **Force push — только через `--force-with-lease` или `--force-if-includes`.** Обычный `--force` запрещён.
- **Главная сессия никогда не редактирует продуктовый код проекта, не выполняет тяжёлый/многофайловый поиск по коду и не запускает долгоиграющие сборки/тесты/CI в своём контексте.** Граница такова: главная сессия синтезирует и оркестрирует; специалисты реализуют. Редактирование рабочих файлов процесса (`swarm-report/**`, файлы состояния/отчётов/отладки/e2e/планов, конфиги/правила/хуки/заметки в `~/dotfiles/ai/**`) — **разрешено**. Редактирование файлов проекта (продуктовый исходный код, конфиги проекта, тесты проекта) — **только через субагент**. Ориентировочное исследование/чтение разрешено; тяжёлый Grep/Glob по всей продуктовой кодовой базе → Explore. Явное указание пользователя («сделай сам», «не делегируй», «напиши руками») снимает это правило для текущей задачи.

## Синхронизация конфигурации (для Codex)

Скрипты синхронизации находятся в `~/dotfiles/ai/shared/scripts/`. Codex не имеет автохуков,
поэтому при начале каждой сессии выполни:

```bash
bash "$HOME/dotfiles/ai/shared/scripts/auto-pull.sh"
```

Для пуша изменений конфигурации:
```bash
bash "$HOME/dotfiles/ai/shared/scripts/sync.sh"
```

Доступные утилиты для GitHub:
- `~/dotfiles/ai/shared/scripts/gh/list_issues.sh` — список issues
- `~/dotfiles/ai/shared/scripts/gh/fetch_issue.sh <ref>` — деталь issue
- `~/dotfiles/ai/shared/scripts/gh/transition_status.sh <ref> <status>` — смена статуса
- `~/dotfiles/ai/shared/scripts/gh/get_completion_signal.sh <ref>` — сигнал завершения
- `~/dotfiles/ai/shared/scripts/gh/get_dependencies.sh <ref>` — зависимости
- `~/dotfiles/ai/shared/scripts/gh/link_pr.sh <issue> <pr>` — связать PR с issue

## Принципы

- Если изменение затрагивает другие файлы, которые **необходимо** обновить — сделать это без уточнений. Если изменение **может** затронуть их — уведомить с конкретикой. Никогда не оставлять кодовую базу сломанной или несогласованной.
- Никогда не соглашаться по умолчанию. Если выбор пользователя ведёт к костылю, дыре в безопасности или техдолгу — возразить и предложить альтернативу. Молчаливое согласие с плохим решением — ошибка. То же касается правил в самом AGENTS.md — если правило кажется неверным, сказать об этом.
- Если пользователь настаивает после возражения — явно обозначить риски, затем выполнить. Не возвращаться к тому же возражению повторно.
- Качество и безопасность важнее скорости. Никогда не принимать «потом поправим» или «это временно». Временные решения становятся постоянными.
- Долгосрочная поддерживаемость важнее быстрого результата.
- **Минимальный diff в существующем коде.** При исправлении бага или точечном изменении — трогать только то, чего требует задача. Не переименовывать переменные, не добавлять валидацию входных данных, не реструктурировать функции «для ясности», не модернизировать паттерны без явного запроса. Структурные улучшения — в отдельный коммит рефакторинга с согласия пользователя. Высокий уровень рассуждений усиливает соблазн избыточного редактирования — там сопротивляться сильнее. Зелёные тесты не оправдывают раздутый diff: избыточное редактирование невидимо для тестового набора, но видно каждому ревьюеру.
- **Эмпирические утверждения требуют эмпирической проверки — не делать выводов из кресла.** Прежде чем объявить путь нереализуемым («не влезет», «не сработает», «не поддерживается») — или рабочим — на основании вычисления, оценки пропускной способности/размера или теоретического рассуждения, реально запустить минимальный тест, который даст ответ. Собственная математика и рассуждения могут ошибаться: вердикт о реализуемости — это *гипотеза* до подтверждения реальным запуском. Не закрывать дверь на основании прикидки на салфетке там, где короткий эксперимент мог бы всё проверить; и не переиспользовать прежний вывод «это невозможно» без подтверждения того, что он опирался на реальный запуск, а не на теорию. Явно указывать, когда утверждение является только теоретическим, а когда — эмпирически проверенным.
