# Глобальные правила AI-агентов

## Неоспоримые правила

Правила, не подлежащие обсуждению. Их нарушение — ошибка, а не вопрос суждения.

- Язык общения - русский
- **Никогда не обходить git-хуки** (`--no-verify`, `--no-gpg-sign`, `-c commit.gpgsign=false` и т.п.) без явного запроса пользователя. Если хук падает — расследовать и устранять корневую причину.
- **Никогда не коммитить и не пушить напрямую в main/master/develop продуктовых проектов.** `auto-pull.sh` только подтягивает изменения и никогда не коммитит/пушит. Репозиторий конфигурации `$HOME/dotfiles/ai` можно коммитить и пушить только по явному запросу пользователя или через явно запущенный `sync.sh`.
- **Force push — только через `--force-with-lease` или `--force-if-includes`.** Обычный `--force` запрещён.
- **Все новые файлы должны быть добавлены в git.**
- **Главная сессия никогда не редактирует продуктовый код проекта, не выполняет тяжёлый/многофайловый поиск по коду и не запускает долгоиграющие сборки/тесты/CI в своём контексте.** Граница такова: главная сессия синтезирует и оркестрирует; специалисты реализуют. Редактирование рабочих файлов процесса (`swarm-report/**`, файлы состояния/отчётов/отладки/e2e/планов, конфиги/правила/хуки/заметки в `~/dotfiles/ai/**`) — **разрешено**. Редактирование файлов проекта (продуктовый исходный код, конфиги проекта, тесты проекта) — **только через субагент**. Ориентировочное исследование/чтение разрешено; тяжёлый Grep/Glob по всей продуктовой кодовой базе → Explore. Явное указание пользователя («сделай сам», «не делегируй», «напиши руками») снимает это правило для текущей задачи.

## Условная загрузка правил

Это постоянно действующее ядро. Перед действием явно прочитать соответствующие файлы из `$HOME/dotfiles/ai/shared/rules/`; не загружать остальные «на всякий случай». Ссылки и `@` в Codex не означают автоматическое чтение. В Claude импортируется только ядро, а маршрутизация ниже выполняется явно. Если область задачи расширилась, прочитать добавившиеся правила до работы в новой области. Специалист получает список применимых rules и читает их до изменений.

| Когда | Прочитать |
|---|---|
| Общение и отчёт | `communication.md` |
| Делегирование/новый адаптер | `runtime-adapter.md`, `orchestration.md` |
| Изменение кода/config/поведения | `code-policies.md`, `workflow.md`, `qa-and-testing.md`; `task-types.md` для выбора baseline/проверки |
| Ошибка, retry, большой вывод или расширение scope | `task-execution.md` |
| Поиск/навигация по продуктовому коду | `ast-index.md` — indexed-search-first |
| Добавление/изменение/чтение логов | `logging.md` |
| Код с внешним API, research, migration | `external-sources.md` |
| Добавление/bump dependency или plugin | `dependencies.md`, `external-sources.md` |
| `.kt`/`.kts`, Kotlin/KMP | `kotlin-style.md` |
| Gradle scripts/catalog/convention plugins | `gradle-style.md` |
| Android markers или Android platform/tooling | `android-cli.md` |

Новые тесты и mobile manual QA — только по явному запросу; единая подробная политика в `qa-and-testing.md`. Project hooks/CI всегда авторитетны. Глубина workflow определяется риском, а не количеством файлов; критерии в `workflow.md`.

## Синхронизация конфигурации

Скрипт `auto-pull.sh` запускается при старте сессии (или вручную, если у рантайма нет
SessionStart-хука). Он подтягивает удалённые изменения, но не коммитит и не пушит. При
локальных изменениях pull пропускается; пользователь может проверить их и явно запустить
`sync.sh` для коммита и пуша:

```bash
bash "$HOME/dotfiles/ai/shared/scripts/sync.sh"
```

## Принципы

- Обновлять необходимые связанные файлы без уточнений; о возможном влиянии уведомлять с конкретикой. Не оставлять код/документы несогласованными.
- Возражать против техдолга, костылей и небезопасных решений, включая правила харнесса; предложить альтернативу. После осознанного настояния пользователя обозначить риск и выполнить без повторения возражения.
- Качество, безопасность и поддерживаемость важнее скорости; «временно» не оправдывает дефект.
- **Минимальный diff:** менять только необходимое для задачи. Не переименовывать, не добавлять validation и не перестраивать код «для ясности». Структурный refactor — отдельный commit с согласия пользователя; зелёные tests не оправдывают лишние правки.
- **Эмпирические утверждения требуют проверки:** до вердикта «работает/невозможно» выполнить минимальный разрешённый эксперимент. Расчёты и прежние выводы без запуска — гипотезы; явно отделять их от проверенных фактов. Эксперимент не отменяет QA opt-in и границы авторизации.
