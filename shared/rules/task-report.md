# Один отчёт на задачу

Для задачи создаётся один `swarm-report/<task-slug>.md`. Main выбирает уникальный kebab-case slug при первом сохранении и передаёт его вместе с путём всем навыкам и специалистам. Этапы, повторные проверки, resume и вложенные подзадачи используют тот же файл; новая самостоятельная задача получает другой slug. Не создавать отдельные отчёты, receipts, state-файлы и подкаталоги по этапам или специалистам.

## Содержание и обновление

В начале: цель/источник требований, scope, риск и общий статус. Далее — только применимые разделы: решения/план, реализация, Debug, Checks, Review, Quality, Acceptance, Research, Spec, Test plan, Tests. Для каждого пункта задачи кратко указать результат или причину, почему он не выполнен. Не создавать пустые разделы.

- На этап обычно достаточно 1–3 пунктов: статус, существенный результат, незакрытые findings/риски. Хранить актуальную сводку, а не дневник действий; исправленные findings сворачивать в результат исправления.
- Для проверок сохранять команду, результат и минимальное основание применимости: code/artifact identity, scope и environment/toolchain. Повторяющиеся данные записывать один раз и ссылаться на них. Не сокращать обязательные AC, blockers, диагноз и доказательства до потери проверяемости.
- Если workflow требует machine metadata, хранить её в одном именованном YAML-блоке своего раздела; не добавлять frontmatter других этапов. Потребители читают свой раздел и его schema/verdict. Глобальный статус не подменяет статусы отдельных проверок.
- Resume cursor/checklist хранить в разделе этапа только при необходимости продолжения; после завершения свернуть в краткий итог, сохранив поля, которые нужны downstream gates. Не копировать полные ответы специалистов, логи, транскрипты, нулевые findings и повторяющиеся таблицы.

Единственный писатель общего файла — main: специалисты возвращают компактный результат в ответе; main объединяет его и последовательно обновляет нужный раздел, сохраняя остальные. При самостоятельном запуске навыка его вызывающая сессия играет роль main. При resume сначала прочитать существующий отчёт; не перетирать чужие разделы.

Постоянные результаты задачи (`docs/specs`, `docs/plans`, `docs/testplans`, исходники, тесты) сохраняются на своих местах, в отчёте — ссылки. Сырые выводы инструментов при необходимости хранить в штатных временных каталогах вне `swarm-report`; долговременное evidence по умолчанию сводить в отчёт, отдельно сохранять только запрошенные пользователем результаты или обязательные артефакты проекта.

Старые отчёты можно читать как evidence при совпадении проверяемого состояния, но новые записи вести в общем файле. Автоматически не удалять и не переписывать прежние файлы. Новый отчёт добавить в git согласно `shared/AGENTS.md`; не менять `.gitignore` и не обходить ignore принудительным `git add -f`, если проект запрещает отслеживать отчёты — явно отметить это ограничение.
